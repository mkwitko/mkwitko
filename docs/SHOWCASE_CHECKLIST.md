## Before any private repository is made public

- [ ] Verify ownership and written rights to publicly redistribute all project code, names, logos, images, audio, dependencies and internal documents.
- [ ] Scan full git history (not only current HEAD) for secrets, production configuration, contact details, personal data and customer data.
- [ ] Rotate active exposed keys, revoke unused credentials, and examine access logs if warranted.
- [ ] Review third-party licenses, payment provider agreements and product/business secrets.
- [ ] Remove or replace real account identifiers and URLs, demo screenshots with personal details, developer home-directory paths, production data exports and service account files.
- [ ] Run build/tests and prepare factual English README with architecture evidence.
- [ ] Reassess git history after any cleanup; rewriting history can require force updates and coordination.
- [ ] Only then use GitHub Settings → General → Danger Zone → Change repository visibility, if the owner has admin access.

## Nonselected repositories

The owner wants all other repositories private. **This checklist does not change visibility:** the current GitHub connector can edit files and PRs but cannot change visibility or profile pins. The owner must use GitHub repository Settings individually, following organization/permission restrictions.

Do not include nonselected repositories in the profile README, website, pinned suggestions, public issues or architecture links.

## Showcase evidence

- Genuine redacted screenshots and 30–60 second walkthroughs, not AI mockups presented as real interfaces.
- CI badges only after checks pass.
- Architecture diagrams with direct source links and documented trade-offs.
- Public demo site only when authorized and appropriately secured.
- Portfolio Pages: enable main /docs and test the logged-out URL before publishing it as live.
